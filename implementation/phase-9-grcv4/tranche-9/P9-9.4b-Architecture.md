# P9-9.4b — public ownership and family-dispatch refinement

The public contract remains one GRC9V4 lifecycle with ten typed scientific
families. Native public execution remains C_OS, C_CI, A_CI and A_PC. This change
implements the user's four architecture recommendations without changing the
scientific equations, numerical policies or serialized checkpoint layouts.

## 1. Execution selection

`PUBLIC_ENABLED_FAMILIES` declares the four public execution families independently
of `grc_9_v4_owner._OWNERS`, which registers technical implementations. The public
selection must be a subset of available implementations. Missing implementations
fail explicitly; adding a registered implementation cannot widen execution.
Contract discovery continues to describe all ten. Neither registry grants full
conformance acceptance.

## 2. Immutable preparation, sole branch publication

`prepare_enabled(context, kind, request)` prepares ordinary steps, expansion,
reset and rebase. `GRC9V4EnabledContext` supplies the admitted scientific state,
receipt history and complete retained artifacts. `GRC9V4EnabledTransition`
returns the source context, target scientific state, operation result and complete
artifact bundle. It owns no lock or journal and cannot publish. Closed action
validation rejects unknown kinds, mismatched request types and extra requests.
The caller selects the explicit numerical backend/policy context.

The standalone enabled owner and the branch owner use this same preparation
logic. Expansion delegates to the existing `prepare_expansion`; ordinary and
administrative preparation reuse the existing kernels, receipts and admission
checks. Transitions validate exact state types, receipt endpoints/parents,
append-only artifacts, and exact source retention on rejection. Each caller
checks that the returned transition belongs to its actual source before commit.

An enabled branch now contains only `GRC9V4EnabledBranch(state)`, an immutable
scientific value. It contains no nested enabled owner, receipt ledger, journal,
lock or retained-artifact store. The branch publication owns the one receipt
history, mixed journal and `GRC9V4EventArtifacts` bundle. After complete admission
and observable validation, it publishes one immutable replacement.

This removes `_clone_enabled`, the cross-owner private receipt write, and the
public artifact-delta slices. There is no second enabled publication to synchronize.
All operations carry the complete bundle; reset/rebase preserve it, while
expansion, profile loss and branch crossing explicitly append their evidence.
`require_extension_of` checks every declared artifact field. A new retained
artifact kind must still have an explicit wire-schema representation.

The standalone owner exports its initial checkpoint, scientific value and
execution choices atomically through `export_seed()`. That preserves the existing
initial-prefix replay contract without exposing a mutable child owner. Native
legacy execution retains its established exact adapter and private-copy rollback;
no GRC9V3 implementation is changed.

## 3. Scientific family dispatch

`GRC9V4FamilyImplementation` associates each exact native state type with its
existing readmission function, expansion constructor and history policy.
Candidate, persistence and reference-current retention are explicit independent
fields. C_CI and C_RG2b retain reference currents without a history policy; those
properties are not equivalent. Named family entries also supply the source
current probe where readmission does not return role currents. Shared code no
longer infers these semantics by parsing a family name or branching on state type.
A shared `GRC9V4FamilyId` alias preserves the individual state validations.

The four selected families receive native integration and replay checks. For the
other six, this work validates routing and structural AST equality of the existing
readmission functions. AST equality is not source-byte equality, and the bounded
fixture/checkpoint comparisons are not a universal equivalence theorem.

## 4. Checkpoint/replay assessment

The actual public load path restores an enabled initial checkpoint and then
executes the outer journal. The public envelope validates the resulting complete
snapshot; it has no additional journal replay of its own. Standalone native
event checkpoints are not nested inside that enabled checkpoint. The branch contains an immutable enabled value; it does not clone or replay a
nested enabled owner during an action.

The architecture execution record measures one small C_OS case: a zero ordinary
step, a canonical expansion and a positive target step, with an empty initial
journal. Instrumentation counts native ordinary and expansion calls during load
and rejects any invocation of standalone event-checkpoint replay. Timing is a
bounded observation of this case, not a scaling benchmark or performance promise.
Nonempty initial journals still require their own legitimate prefix replay;
constructor/readmission work also has a cost.

Measured on this checkout: construction 0.338 s;
three forward actions 3.623 s; full public load
3.846 s. Load executed exactly two ordinary steps and one
expansion, with zero standalone event-checkpoint replays. These timings were
collected alongside the parallel verification processes.

Decision: retain current checkpoint layouts and full replay verification. The
alleged fourfold replay is not a justification for migrating accepted formats.
The record's measured counts/times provide a concrete baseline for a future
assessment. No digest-only substitute or automatic numerical fallback is added.

## Future consideration: one owner, one journal across every format

**Revisit after all ten families are fully enabled and their lifecycle behavior
is established.** Current branch execution already has one publication/receipt
history/journal for enabled actions and crossings. The broader optional question
is whether standalone event, standalone enabled, branch and public checkpoint
formats should converge on one closed action vocabulary and versioned format.

This is not a deferred repair for private enabled-owner access: that dependency
has been removed. Future format consolidation must demonstrate a concrete
maintenance or replay benefit, preserve exact legacy behavior and scientific
handlers, and provide explicit import/version adapters for historical checkpoints.
Preserve original accepted execution evidence. The ten-family milestone does not
authorize silently rewriting it or replacing replay validation with digest checks.

## Evidence and compatibility

[P9-9.4b-architecture.json](P9-9.4b-architecture.json) retains scope-isolation,
ten-family routing, artifact-prefix preservation, rejection/late-failure rollback,
byte-for-byte predecessor event checkpoint comparison for the four families,
unchanged replay of accepted P9-9.1b mixed and P9-9.4a crossing checkpoints,
sole branch ownership, stale-transition rejection, and the replay assessment.
The main [review](P9-9.4b-Review.md) links fresh public integration runs.

Historical records remain unchanged. `p994b_runtime_successor.py` recognizes only
the named current runtime hashes and committed predecessor hashes, including the
P9-9.4a rejection-only owner correction. It authenticates the old execution source;
it does not relabel historical results as execution of the new implementation.
Fresh P9-9.4b records bind the successor, and unrelated source drift still fails.

The historical 8.5 reader now compares its recorded input population with the
same recorded paths, rather than adding later files discovered by a current-tree
scan. Exact named source/metadata predecessors are retrievable from Git; the
8.5/8.6 projections authenticate those original bytes and preserve acceptance.
This fixes a reader incompatibility, without rerunning or rewriting historical
execution. It gives no current-code numerical conformance claim.
