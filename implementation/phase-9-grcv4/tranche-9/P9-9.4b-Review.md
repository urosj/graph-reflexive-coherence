## Public architecture

`from pygrc.models import GRC9V4` lazily exports `GRC9V4(GRCV4)`.
The [public API guide](../../../examples/grcv4/grc9v4_api.md) describes typed
construction, state and discovery, with examples and the five-realization table.

`grc_9_v4_contracts.py` defines ten family descriptors, an immutable
`GRC9V4Configuration`, explicit execution options and readable branch-specific
state. It reuses the existing candidate/realization parameter types: A/C and
OS/CI/PC/CI+PC/RG2b retain their own scientific fields and solve semantics.
Candidate A alone owns W_A; PC and CI+PC independently own Z_4. Authority
presence/dimensions are validated for both current and reset. CI joint roots and
RG sections remain derived objects. There is no fabricated common solver schema.

Configuration accepts scientific inputs directly, without internal stage
wrappers or caller-computed state identities. It validates and round-trips all
ten families without constructing their numerical owners. All ten catalog small
source declarations pass. Native construction of the other six raises the typed
`GRC9V4ExecutionUnavailable` before a kernel or owner is invoked.

`grc_9_v4.py` is the facade; `grc_9_v4_api_lifecycle.py` owns transaction
composition and delegates admission and numerics to the existing native owners.
No current, history, geometry or admission equation changes. Explicit backend
and numerical policy are retained through replay, with no inferred fallback.
The earlier low-level native constructor remains available for serialized inputs.
Enabled state exposes graph, profile, specialization, current authority,
independent reset, clocks, identities and receipts. Disabled state exposes an
exact native checkpoint with detached access, preserving native JSON signed zero.
The complete replay checkpoint is separate from this readable state view.

The [architecture refinement](P9-9.4b-Architecture.md) makes public execution
selection independent of native registration. Every enabled action prepares an
immutable transition; the branch owns the sole receipt history, journal and
complete artifact bundle. There is no nested enabled owner, private receipt
synchronization or artifact-delta slicing. Scientific descriptors explicitly
separate candidate, persistence and reference-current retention.
Nine architecture tests compare predecessor checkpoints, replay accepted mixed
and crossing histories, pressure rollback/stale transitions/artifact loss and
measure the actual load path. Standalone/branch checkpoint-format consolidation
remains a future consideration after all ten families are fully enabled.

The facade exposes typed explicit steps and `run_v4`, canonical expansion,
profile and enabled/disabled branch migration, observables, immutable complete
state, reset/rebase, duplicate, save/load and mixed-journal replay. `step()` and
`run(n)` on the enabled branch require the identity-bearing serialized default
request. The native disabled branch instead uses its exact configured native
step. A supplied V4 dt/context on that branch rejects rather than being ignored.

Enabled observables include native port occupancy/degrees, row gradient, signed
row Hessian, net flux, coarse column totals/profiles, mechanical expansion count,
branch and exact compatibility target. Exact rational coarse ratios serialize
as strings. Candidate detection is labeled available only on a successful
positive ordinary step's fresh postbeat; a standalone read does not invent a
trigger stage. The selected step current and its continuity provenance remain
in the step result. Persistent receipt history includes the newly emitted delta.
The disabled observable projection remains exactly the native target's output.

`describe_families()` describes all ten public contracts. Exact local
`list_declared_profiles()` can include any of them. `list_supported_profiles()`
filters registered declarations by execution scope and current graph.
After expansion, stale source-graph targets do not appear as current targets.
Full GRC9V4 conformance and the forty-cell compatibility capability are not
advertised. The executable-family population remains the selected four; numerical
admission is still required for every actual state/target. `support_status()`
makes these limits explicit. No global G3 support is granted by importing a class.

## Profile and branch migration boundaries

Same-candidate profile migrations reuse the accepted history mapping, followed
by native both-role readmission and typed native endpoint receipts. Carrier loss
is explicit and archived. The tests execute C_OS↔C_CI and A_CI→A_PC→A_CI.
The original retained A_PC state **rejects** direct readmission into the retained
A_CI domain (`CI bounded map is not certified to be a self-map`). That negative
result is retained in the A_PC record. The passing return case starts from the
already admissible A_CI state migrated into A_PC, with unchanged CI parameters.
No universal pairwise migration domain is claimed.

A direct C→A profile request is explicitly rejected: the generic WLS initializer
cannot substitute for the fixed-port initializer. Accepted branch entry/return
accepts an explicitly declared native initialization stage for this purpose.
This is an exposed API limit, not a newly accepted transport law. Both branch
directions, their loss/initialization rules and exact disabled projections are
executed through the public class for all four selected families. Crossings
retain 9.4a's same-graph restriction; legacy topology growth is not an inferred
return map. Generic mapped events/representation transport cannot bypass the
canonical native chart/expansion receiver.

## Saved selections

[run_selection.py](../../../examples/grcv4/run_selection.py) verifies a saved
catalog selection before importing/constructing a runtime owner. Complete native
state selections decode to public configurations. The existing native-oracle selections are
reconstructed from their pinned scientific clock, both histories, reference and
specialization; native state/reset/model identities must match exactly. Configuration extraction covers all ten and preserves their typed parameters.
Actual execution remains four-family. A fresh construction does not claim
historical receipt lineage; complete snapshots serve that separate purpose.
Unsupported recipe formats reject explicitly. Selecting a larger fixture does
not make it admitted or repeat its historical run automatically.

A small source selection can be executed from the repository root:

```bash
python examples/grcv4/catalog.py select native-small-C_OS --side source --output outputs/selections/c-os.json
PYTHONPATH=src:. .venv/bin/python -m examples.grcv4.run_selection outputs/selections/c-os.json --requests outputs/requests.json --exact-backend flint --numerical-policy legacy_exact_v1 --output outputs/c-os-public.json
```

`requests.json` is an explicitly supplied ordered array, e.g.:

```json
[{"schema_version":"grcv4-step-request-input-v1","operation_id":"example-1","dt":0.000244140625,"context_value":{},"boundary_input":null,"external_source":null}]
```

An empty array constructs only. The runner never overwrites output; records
larger than 1,000,000 raw bytes use `.json.xz`. Backend/policy are required inputs.
