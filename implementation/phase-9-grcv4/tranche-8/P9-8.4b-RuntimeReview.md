## Execution and failure semantics

Each case records source admission, one actual source beat and reset
preservation, fresh candidate/request, one native event and its actual
checkpoint/receipts, exact both-role transfer, ten target beats per role and
final reads at `dt=1/4096`. Observation of the production OS admission calls
checks both source and both target histories while the old source publication
is still live. Target continuations are independent role branches, not twenty
steps on one live state or two committed topology events.

The runner checks unchanged event clock, one resource write per ordinary beat,
absent A/carrier history, preserved reset baseline, nonnegative resources and
exact event charge relative to each actual incoming role. The rounded source
beat's charge is not assumed to equal the nominal Q as an exact rational.
Final readmission does not advance the clock or create a topology event.

The first failure retains its owner/stage and unexecuted dependent stages.
An actual committed event remains recorded even if later comparison or
continuation fails. A timeout is operational incompletion, never mathematical
rejection or success. The runner refuses to overwrite an existing run file.

[COSResults](./P9-8.4b-COSResults.json) is the execution record. Its manifest
digest binds the exact inputs/checker, and it retains dependency versions,
thread settings, actual numerical comparisons, state/receipt identities,
timings and any failures. Review and user acceptance remain separate from its
per-case execution outcomes. P9-8.4b and aggregate P9-8.4 remain open.

The campaign took 265.34 seconds summed over case execution. Fourteen successful
cases establish 28 complete history cells. Sixteen actual events committed;

failed cases execute no target beat and do not attempt reset continuation or

### D52 phase one is not a continuation witness under this recipe

For both chiralities, `/extra/1/1` receives zero resource at the event. The
independent OS calculation predicts its first value as approximately
`-0.0003544455590641839`, a rate of `-1.4518090099268972` at `dt=1/4096`.
Production rejects that beat at the nonnegative-resource boundary. The event
itself remains committed, exactly as its separate readmission obligation allows.

This is far outside the comparison budget and is reproduced independently,
not a tolerance or representation discrepancy. Because the incoming resource
is zero and the OS read is duration-independent, reducing positive dt scales
the negative value without changing its sign. Clipping or relaxing admission
would change the contract. Phase two/three and the smaller layouts remain
separate successful observations, not counterarguments to this failure.

The [two focused regression tests](../verification/test_p984b_cos_phase1.py)
reproduce both native rejections, compare the independent negative values,
check the half-duration sign, and ensure unexecuted reset/final stages are not
reported as successes. A separately identified lawful resource/share recipe
and its independent continuation expectations are needed before those two
positive cells can close. The separately bound successors below provide those
positive witnesses without replacing this original result.

## Phase one successors and reporting hardening

The [successor runner](../verification/p984b_cos_successor.py) reuses the original
execution contract and adds observation of the actual consumption path. Its
[inputs](./P9-8.4b-COSPhaseOneCases.json) bind exactly two D52 phase-one cases,
one per chirality, before native execution. The source, current/reset states,
profile, reference weights, timestep, ten-beat horizon and numerical tolerances
are unchanged. Only the request shares change from `(1/2, 1/4, 1/4)` to
`(1/4, 1/2, 1/4)`, with new operation and computed event/target identities.
This is permitted by the existing `event_supplied_simplex3` resource contract;
it is a named supplied request, not an autonomous allocation rule or new
scientific authority.

The design diagnostic is the unit-reference, uncoupled limit. With unit
transport weights, `eta_C=kappa_Phi_C=1`, and `kappa_M_C=zeta_C=0`, the boundary
rate is `L² C`, where `L=B Bᵀ`. The original half-share on the doubly extended
branch makes the current-role rate at `/extra/1/1` approximately `-1.451809`.
Giving that branch one quarter and the next branch one half makes every
initially zero node's rate positive for both histories. The successor manifest
retains the exact rational stencil values for both the old and new requests.
This disabled-coupling calculation explains the choice; it does not prove
the enabled law. The enabled dense ten-beat preflight is separately retained
before execution. There was no parameter search, resource clipping or
tolerance relaxation.

Both native successors pass all declared stages. Their
[execution record](./P9-8.4b-COSPhaseOneResults.json) retains two events, forty
target beats, four final role reads and 46 consumption captures. Execution
took 56.22 seconds across the two cases. The minimum observed postbeat resource
over the ten-beat schedules was approximately `1.17234898007222e-5` for current
and `1.22070318641517e-4` for reset. The largest reported dense comparison error
was approximately `5.063e-14`, within the unchanged componentwise budget.
These are measured finite-run values, not rigorous lower/error bounds, an
effect-separation margin, or a uniform parameter tube. Equal outcomes between
these two named cases do not replace the later covariance work.

For each new ordinary step the checker binds the selected current and geometry
from the resource consumer to the OS corrector, reconstructs staged binary64
continuity directly from oriented edges, checks the delivered poststate, and
checks the final refresh at the written C and consumed geometry. Read-Back is
also checked through its causal one-form and Hodge, with its current and source
identity bound. Retained checking links these captures to the arrays reported
as actuals and checks the full source/continuation chain. The existing dense
current oracle remains an independent implementation reused from the generic
tests; conceptual independence is not guaranteed by these additional checks.
The original fourteen successful runs do not retroactively acquire consumption
captures. The new command reports that limitation explicitly.

Use `p984b_cos_successor.py --check-retained --original` for the preserved
campaign, and `--check-retained` for the two successors. Output separates
`events_committed`, `complete_cases`, `all_required_cases_passed`, per-case
`case_passed`, and `native_trajectories_rerun=false`. Thus the original report
says 16 committed events but only 14 complete cases. Exit zero means retained
integrity, not complete numerical success or acceptance. The original runner's
legacy `--check` banner is preserved with its bound source bytes; the explicit
successor command is the current reporting entry point. Only `--run` executes
native trajectories, and it still refuses to replace an existing result.

Twelve [new focused tests](../verification/test_p984b_cos_successor.py) pass,
along with the two unchanged original phase-one rejection tests. They pressure
