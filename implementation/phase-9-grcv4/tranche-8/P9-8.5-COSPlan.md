# P9-8.5 C_OS: internal lifecycle and atomicity

Frozen execution scope, 2026-10-26. Consume the accepted first-group
[8.4i handoff](P9-8.4i-FirstGroupReview.md); C_CI, A_CI and A_PC remain separate.

1. Small accepted native C_OS subject: event/replay endpoint occupancy,
   complete checkpoint equality and receipt/reference identity.
2. Actual event owner: missing chirality, missing active phase, extra inactive
   phase, source self-loop, target readmission; check the complete publication
   pointer, checkpoint, scientific/lifecycle identities and receipt ledger.
3. Genuine reset-only OS split rejection with a passing current control;
   injected final-publication failure after target readmission.
4. Replay rejects altered target current/reset, receipts, request and identities;
   incomplete reference-map reconstruction rejects. An injected rejection is
   identified as such, never called a natural numerical exclusion.
5. From the replayed small event target, construct the existing generic lifecycle
   owner with the identical port reference and both authorities. Execute one
   ordinary step, snapshot/restore, reset, and snapshot/restore again. Check reset
   baseline, clocks, ledger extension, independent resource transfer and full
   rollback on injected reset publication failure. Bind this continuation seed
   explicitly to the event checkpoint: the generic owner's fresh ledger is not
   the specialization's event ledger. This is internal component composition,
   not the Tranche 9 public GRC9V4 facade or its serialized model family.
6. Replay the accepted 100-to-107-vertex `.h` event checkpoint once through the
   real C_OS owner. Require exact original checkpoint bytes, both-role fresh OS
   readmission, unique target occupancy and all four receipts. No new trajectory,
   covariance sweep, scientific oracle or broad boundary rerun.

Small suite cap: 300 seconds. Larger replay cap: 1200 seconds. Single-thread
FLINT, explicitly selected fixed Arb256 policy and the existing exact-content
schema memo (eight entries, at most four MiB each); no precision/fallback switch.
The small, already established tight split counterexamples run separately under
`legacy_exact_v1` to establish actual rejection. The same reset-only case under
Arb256 must report `CertificationInconclusive` and preserve the full publication;
these are two explicit tests, not automatic retry or equivalent proof claims.
Two independent workers may run concurrently. Retain compact observations,
case roster, original input hashes and actual execution-source hashes; reuse
the original large checkpoint by reference. Budget 150 KB per result, 400 KB
total new evidence. Any raw evidence over 1 MB must use lossless compression.
Interrupted runs are disposable. Retained checks authenticate evidence and
scope; only explicit `run-small`/`run-large` rerun native operations.

Completion is bounded C_OS 8.5 evidence pending user acceptance. All-ten 8.5,
other first-group families, 8.6, public support and G2/G3 remain unchanged.
