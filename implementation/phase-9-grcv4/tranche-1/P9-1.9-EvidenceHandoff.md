# P9-G1 evidence handoff and proportionate retention

This is the user-requested retention clarification and preservation addendum,
not a new gate or acceptance decision. P9-G1, its exact scope, all pending
runtime gates, and the original acceptance/execution records remain unchanged.

## Retain substance, not every attempt

Preserve the selected execution evidence that supports an accepted result,
with its input/checker identities, output hashes, and a retrievable location.
A small repository bundle is sufficient; larger outputs may use a genuinely
retrievable content-addressed store with a tracked manifest.

Routine debugging attempts do not require permanent raw archives, separate
manifests, checklist entries, or review. A brief account of a relevant failure's
cause, correction, and remaining limitation in the existing leaf record is
sufficient. Raw failure evidence is needed only when material to substantiating
a limitation, rejection, disputed result, or contradiction of an accepted claim.
Do not hide unresolved contradictory evidence behind a passing rerun.

This clarification supersedes the blanket retention of every failed attempt
in the historical P9-1.5 retention guidance for current Phase 9 work. Those
historical bytes remain unchanged. The seven existing runtime-evidence filenames
describe published supporting runs, not paperwork for every local test attempt.
Once supporting evidence has deliberately been published, it remains immutable;
this does not impose a duty to publish every failure. No existing local archive
is deleted by this change.

The association is post-hoc preservation of existing execution records, not a retroactive
signed attestation: original review records did not pin these output digests.
The manifest records exact run IDs, original receipt/report digests, historical
input bindings, and both original and published byte hashes. It neither asserts a new execution nor dates a run
from filesystem timestamps. Future reruns have their own identities and must
not silently replace its original subjects.

### Path normalization and hash citations

Machine-local checkout, home, attachment, and temporary prefixes have no role
in evidence retrieval. The published copies replace them with repository-relative
input paths or the descriptive labels `<checkout>`, `<temporary>`, and `<user-home>`.
Temporary directory suffixes remain distinct, preserving which isolated checkout
each trace describes. Labels in recorded commands are evidence annotations,
not runnable command substitutions. Values, outcomes, run IDs, and claim/input
identities are unchanged; this is not a new run.

Each archive/member has an `original_sha256` for citation and a `sha256` for
verifying the published bytes. Embedded receipt/report/object hashes still name
the original pre-normalization objects. Separate `normalized_receipt_digest` and
`normalized_report_digest` values validate their published presentations; the
original digest fields must not be recomputed and relabeled as original.

The original ZIP remains in ignored local storage, outside the publication set.
A clone retrieves the normalized records and original hash citations, **not the
original raw ZIP**. A hash citation alone cannot establish original-byte retrieval
or prove the transformation. When an original archive is available, the optional
`--original-archive <local-file>` check verifies its original hashes and compares
every published member with its deterministic path-only normalization.

The current [P9-1.6 snapshot](../verification/history/P9-1.6-ArtifactSnapshot.json)
likewise labels its normalized presentation and retains original hashes. Historical
replays still use the original Git revision, not this normalized snapshot. The
[phase-opening review input](../verification/inputs/P9-PlanningReview.md) is now
repository-local and byte-identical to the originally hash-bound attachment.

The initial P9-1.6–1.8 failed raw report was overwritten before archival existed.
Its [existing audit-closure summary](./P9-1.6-1.8-AuditClosure.json) remains the
record; no reconstruction is claimed. Other relevant development causes and
corrections remain in the unchanged [G1 execution record](./P9-1.9-ExecutionRecord.json).
Intermediate failed-attempt archives are intentionally not part of this bundle.

## Retrieval and verification

After checking out the handoff changes, run from the repository root:

```bash
.venv/bin/python implementation/phase-9-grcv4/verification/handoff_evidence.py
```

This checks the ZIP, every published member's size/hash, original identity references,
normalized receipt/report digests,
and the exact historical Git input bytes without rerunning their checkers. A
normal clone containing `6e0a507` and `a04158e` suffices; no ignored outputs,
network service, notebook server, or browser installation is needed. The script
uses only Python's standard library. A shallow checkout missing these commits
must retrieve the recorded history for historical-input verification.

The standard ZIP can be opened directly to inspect the normalized JSON, logs and
images. Its member names mirror their original generated locations. Do not
extract it over the current generated directory: those are different execution
subjects. The manifest's artifact hashes make individual extracted files
checkable as well.

The full Phase 9 verifier reports `handoff_evidence.status` separately as
`verified`, `unavailable`, or `invalid`. The standalone command above fails on
missing or invalid evidence; a rehashed replacement manifest cannot silently
replace the published identity. Neither archive status nor the archive bytes
participate in implementation permission or the current implementation-tree hash.
The API, notebook, browser, and downloaded status expose the same distinction.

`P9_G1_accepted` authenticates the original user decision. A current source or
scope violation still fails the implementation boundary and sets
`runtime_authorized: false`, without rewriting recorded acceptance. An invalid
or unavailable acceptance record cannot supply a positive acceptance claim.
No runtime conformance is granted by any of these checks. Latest files under
`tool/generated/phase9-verification/` remain disposable working outputs, and
automatic local pressure archives need not be published or reviewed. Publish
another selected bundle only when another accepted result needs handoff evidence.

The integration check initially stopped at browser-test discovery because
Playwright loaded an imported browser module as CommonJS. The test now uses
an independent fixture serializer; this was a harness issue, not a failed
archive, acceptance, or source-coherence check.
