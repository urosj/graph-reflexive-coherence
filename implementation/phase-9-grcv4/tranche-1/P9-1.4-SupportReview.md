## Migration applicability and gate holds

All seven classes from the frozen migration policy matrix remain registered.
With only C_OS available, positive nonhistory-to-nonhistory migration is
required. Crossings involving A, PC, CI+PC, or other unavailable endpoints
remain visible as pending positive evidence, not fabricated passing cases.

The interface explicitly requires rejecting a target absent from
`list_supported_profiles()` before provisional mutation. These negative
checks are required but do not satisfy a positive crossing fixture.
An unavailable source cannot be instantiated solely to pretend to execute a
migration; constructor rejection is recorded as constructor rejection.

At G2 review, record each class by exact source/target identities and distinguish
positive execution, negative boundary execution, source-backed nonapplicability
to the declared subset, and remaining holds. There is no automatic waiver for
`ALL-MIGRATION-CLASSES`: if the frozen contract requires a case that the proposed
subset cannot execute, hold that gate and explicitly review the necessary
scope/evidence extension. Do not weaken the specification or silently implement
another profile to make the gate green.

project handoff can therefore remain held while a narrower, fully evidenced
specialization scope is conformant. Unselected completion stays visible as
planned/deferred; it never receives a fabricated execution result.
