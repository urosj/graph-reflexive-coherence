## Implemented boundary

- `GRCV4StepResult` and `GRCV4LifecycleResult` now own typed, detached failure
  details and receipt envelopes. Step results support closed primitive/JCS
  reconstruction. Result equality uses canonical JSON, not loose Boolean/number
  mapping equality. Integral step-index storage is checked before normalization.
- `GRCV4Failure` checks scientific/lifecycle pre/post labels and nested receipt
  labels. Result construction checks the operation/solver split: pre-solver
  rejection has no solver status; candidate-solve rejection retains the failed
  disposition; post-solver step rejection retains `valid_root`. Lifecycle
  results do not invent a step solver. A failure result emits its failure
  receipt, not successful receipts or a persistent ledger.
- `SuccessfulReceiptEnvelope` validates each closed versioned receipt payload
  and content identity. Payloads remain immutable primitive declarations;
  constructing migration/history/compatibility receipt shapes does not execute
  those operations. The existing frozen loss ordering is enforced by the schema.
- `CommitPayload` and `make_commit_receipts` follow receipt payload → receipt
  ID → commit payload/ID → envelope, without a self-hash cycle. They construct
  content records; no model or persistent ledger is written.
- `bind_step_result` revalidates even typed inputs and compares the exact
  request, captured scientific pre/post payloads, ordered pre/post ledgers,
  separately supplied observed stage/code/solver, result and commit preimage.
  It checks source/target state and authority identities, the generic model/
  profile binding, receipt-to-commit links in both directions and the ordered
  emitted delta. Rejection requires equal scientific payload bytes and equal
  full ledger envelopes, including commit IDs not present in the lifecycle
  digest preimage. Success requires exactly prior ledger plus emitted delta.
- Events retain common `GRCEvent` projections. This implementation uses
  `source_graph_digest`, `target_graph_digest`, `source_model_identity`,
  `target_model_identity`, `source_profile_id`, `target_profile_id`, `commit_id`
  and `receipt_id` in the open event payload to carry the required bindings.
  The comparator checks these against this operation's emitted receipt, model
  and committed clock. This is an implementation key convention, not a new
  frozen event schema or a topology-event execution claim.
- `negative_duration_result` composes the actually executed pure rejection
  prefix against supplied captured state/ledger payloads. It returns a rejected
  result plus detached comparison evidence, no solver status, commit or ledger
  append. Zero/subnormal/extreme positive inputs cannot obtain a completed step
  through this helper.

## Audit follow-through and limits

The P9-2.3 audit's wrong-source, foreign-operation/stage/code, rehashed receipt,
request-versus-receipt identity and delta/ledger distinction now have tests at
this new comparison boundary. Different negative requests may share a receipt;
their exact request bytes remain separate in `StepResultEvidence`. Evidence
objects are ordinary immutable values, not an admission token or replay permit.

The owner must capture **actual** state and outcome values; it cannot obtain
them from an imported receipt and call that observation. This leaf compares
scientific digest preimages and complete supplied ledger envelopes. It does
not independently reconstruct graph/profile/reset content behind their labels,
validate charge/geometry/domain/history semantics, execute a candidate or writer,
authenticate an observer, or roll back a mutable model. The hand-computed
positive and post-solver charge examples establish composition checks, not an
executed solve or complete atomicity. P9-2.5 and the full-step/lifecycle owners
retain those real-operation tests.

The comparator is generic GRCV4-only: a GRC9 model label cannot establish its
underlying generic profile, so specialization binding fails closed until that
owner exists. The two frozen GRC9-labelled result fixtures still reconstruct
as content records; this is not GRC9 runtime conformance.

The accepted P9-2.1 ownership tests now use independently hashed, complete
receipt fixtures instead of deliberately unvalidated labels/partial failure
maps. All original ownership assertions remain, adjusted for typed projections.
Canonical equality/ordering, mutation isolation and unknown-field rejection
remain enforced. Old published source/test/run bytes remain retrievable at the
accepted commits; no prior evidence was overwritten.
