# P9-1.6 — Successor Verification Pressure Guide

**Date:** 2026-09-05
**Role:** prospective audit guidance, not a review of submitted P9-1.6 code
**Scope:** successor verification and routing from the normal tool entry point
**Authority effect:** none; this note neither accepts P9-G1 nor authorizes runtime work

## 1. The central acceptance question

P9-1.6 should answer:

> Can the normal verification entry point validate the actual Phase-9 review tree, under the correct successor authority, while retaining the frozen historical checks and making no stronger claim about implementation permission, runtime execution, or scientific support?

It should not merely make the command return zero. There are two equally important failure modes:

- **False acceptance:** historical checks are skipped, a broad path exception admits unreviewed work, or a planning record is treated as runtime authority.
- **False rejection:** the historical auditor is applied outside its historical envelope, its old `implementation_authorized=false` becomes a permanent veto, or legitimately authorized uncommitted review artifacts are treated as invalid merely because they are uncommitted.

The source plan separates these work items:

- **P9-1.6:** successor verifier and normal-entry routing.
- **P9-1.7:** adversarial mutation-policy verification.
- **P9-1.8:** affected tool/API/notebook/browser surfaces and authority labels.
- **P9-1.9:** accepted P9-G1 successor authority before runtime work.

Use the pressure cases below to design P9-1.6. Keep execution credit for P9-1.7 and surface reconciliation for P9-1.8 separate. Implementing a route does not complete those dependent leaves automatically.

## 2. Source basis and evidence ceiling

This guide is grounded in the supplied updated Phase-9 plan, checklist, opening, and P9-1.4/1.5 review package. Their relevant requirements are:

1. preserve release-bound historical auditor/boundary bytes;
2. evaluate historical assertions against their accepted historical revision;
3. verify the present tree through an explicitly authorized successor;
4. do not infer authorization from a branch name, a flag alone, or old acceptance;
5. retain current claim, debt, and support semantics;
6. keep planned profiles separate from accepted runtime support;
7. keep the normal-entry issue visible until its applicable dependent verification closes.

No P9-1.6 implementation or result package has been audited in this note. The following are proposed tests and reporting requirements, not claims that defects have been found or tests have passed. Suggested reporting fields are illustrative; existing accepted schemas and disposition names remain controlling.

## 3. Historical truth and current authority need different subjects

### Required distinction

A historical check concerns one immutable source revision. A current-tree check concerns the actual checkout and its admitted changes. Neither substitutes for the other.

For each result, retain:

- verifier code identity;
- historical baseline/release identity;
- evaluated tree or file-manifest identity;
- dirty/staged/untracked changes relevant to that evaluated scope;
- authority record identity and predecessor chain;
- exact scope of the conclusion.

The historical run must not accidentally import current helper modules or resolve current fixtures through a working-directory path. The preserved historical script alone is insufficient if its dependencies come from a different revision.

Likewise, a historical success must not certify a newer tree that was never evaluated.

### Pressure cases

**Historical success plus current frozen-file corruption.** Change one byte in a current release-bound member. Historical validation should still describe the historical snapshot, but current release integrity must fail. The overall current-tree result cannot remain green.

**Current authorized review additions plus old historical false flag.** The old flag remains a correct historical fact. The current review tree can be permitted while runtime authorization remains false. Do not rewrite the old flag or force the old auditor to recognize future paths.

**Mixed revision.** Combine an old auditor with newer helper/fixture bytes. Detect the identity mismatch or decline historical attestation; do not call the resulting execution a reconstruction of the accepted historical check.

**Unavailable historical material.** A missing commit, file, or required dependency means historical verification could not complete. It is not a successful skip and is not automatically evidence that scientific authority is wrong.

## 4. Successor dispatch must not be an error-suppression fallback

The dangerous architecture is:

```text
run historical checker against current tree
if it fails for any reason:
    try successor checker
    accept if successor prints a pass marker
```

That can convert a changed frozen source, parser failure, missing input, or checker exception into apparent success.

Instead, resolve the permitted evaluation mode from validated authority first. Run the historical and current obligations applicable to that mode, and combine their results without dropping a required failure.

### Double checks

- Missing successor authority does not select a permissive default.
- A malformed successor record does not trigger legacy-mode fallback.
- Two conflicting successor records do not resolve by filename, modification time, or largest version number.
- An exception, timeout, unavailable dependency, missing output, or partial result cannot count as a pass.
- Exit status, structured result, evaluated scope, and retained output agree; a printed `PASS` substring is not sufficient.
- The dedicated successor command and the normal entry point evaluate the same inputs and policy version.
- Verification does not silently repair manifests, regenerate accepted hashes, change gate flags, or remove offending files before checking.

The historical phase-envelope failure explaining P9-TOOL-001 is specific. It must not become an exemption for every failure emitted by that historical checker.

## 5. Authorization cannot be manufactured by the candidate record

A matching hash establishes consistency with particular bytes. It does not independently establish that those bytes were authorized.

The candidate tree must not be able to authorize itself by changing `implementation_authorized` and recomputing nearby digests. Permission needs the declared accepted predecessor and review/acceptance chain, rooted in independently identified accepted inputs.

This does not require inventing a new signature system. It requires making the existing trust anchor and accepted transition explicit.

### Pressure cases

- Flip `implementation_authorized` to true without the accepted P9-G1 successor.
- Repeat that mutation and recompute every digest the candidate itself controls.
- Copy an otherwise valid gate from a different release or baseline.
- Leave all predecessor IDs present but alter one referenced predecessor's bytes.
- Add a future gate ID to a checklist without its acceptance record.
- Supply a self-referential or cyclic predecessor chain.
- Provide both a valid planning record and a contradictory claimed runtime record.

All should reject the claimed promotion or produce an explicit unresolved-authority hold. None should create runtime authority.

A proposed module path in P9-1.5 is not permission to create that file. A successful verifier run is not reviewer acceptance. Conversely, an explicitly authorized review package can be valid while its engineering conclusions still await acceptance.

## 6. Mutation scope must be precise in both directions

The P9-1.5 register distinguishes 133 frozen legacy references from two separately reviewable additive integration targets. Neither category gives unconditional permission to modify files during P9-1.6.

Particularly important examples are:

- `src/pygrc/models/grc_v4.py`: proposed future V4 code, not presently authorized simply because its name appears in the plan;
- `src/pygrc/models/__init__.py`: future narrowly reviewed additive exports, not blanket edit permission;
- `pyproject.toml`: future optional dependency changes, not permission to alter unrelated dependencies or package behavior;
- frozen auditors/specifications: not editable to make their own checks pass.

### Recommended mutation matrix

| Input change | Expected scope decision |
|---|---|
| Explicitly authorized P9-1.6 verifier/review additions | Permit only under the current bounded preparation authority. |
| Authorized plan/checklist progress changes | Permit while preserving the exact bound predecessor records and truthful status. |
| New V4 production source before P9-G1 | Reject; a planned filename is not runtime permission. |
| New V4 production source under a valid future P9-G1 fixture | Permit only the exact authorized scope; keep independent regression/integrity checks. |
| Existing legacy source altered under a V4-looking directory rule | Reject. |
| A release member or historical boundary changed and locally rehashed | Reject against the accepted anchor. |
| Authorized additive export plus an old export rebound | Reject the unauthorized portion; filename permission is insufficient. |
| Untracked importable verifier/helper changes | Include in evaluated executable scope; do not ignore merely because untracked. |
| Authorized uncommitted review package with exact byte bindings | Do not reject solely for lacking a commit. |
| Unrelated work outside the declared review scope | Report separate scope and authority; do not silently certify it or delete it. |

Check committed changes after the accepted baseline as well as staged, unstaged, and relevant untracked inputs. A clean worktree is not proof of authorization: an unauthorized edit can already be committed.

Check deletions, renames, file-type changes, and symlink/path escapes, not only ordinary modifications. A path resembling an allowed prefix is not necessarily inside the allowed path. Any unsupported representation should receive a narrow diagnostic, not silent normalization into permission.

Future-state permission tests belong in isolated fixtures. A simulated accepted P9-G1 record must never become the live repository's authority or advance its real gate.

## 7. Protect claim meaning, not just population counts

### The central source distinction

P9-REVIEW-001 explicitly preserves the D10.2 support dispositions `indeterminate_requires_review` while retaining the accepted specification as implementation authority. P9-1.6 should expose that distinction, not resolve it by changing either side.

Do not infer:

```text
accepted specification => every forensic support association is proven
```

or the opposite:

```text
indeterminate support association => the accepted specification is unusable
```

### Preservation projection

Compare source-bound identifiers and their meanings, not only totals. For each relevant entity or association, retain its type, source binding, classification, scope, support disposition, claim ceiling, predecessor relation, and evidence kind.

High-value semantic mutations are:

| Mutation that can preserve totals | Required detection |
|---|---|
| Change one conditional claim to normative | Reject unintended scientific promotion. |
| Change `indeterminate_requires_review` to supported | Reject support-edge promotion. |
| Turn the optional Candidate C profile into a universal requirement | Detect the lost profile scope. |
| Promote a GRC9-only port contract into generic GRCV4 | Detect specialization leakage. |
| Change one planned profile to accepted runtime support | Reject unsupported capability promotion. |
| Replace one compatibility cell with a duplicate of another | Detect exact ID/set mismatch despite unchanged count 40. |
| Count an evidence alias as a second execution | Detect duplicate credit. |
| Convert a deferred obligation into nonapplicable solely because unimplemented | Retain its actual applicability/hold. |

Also retain the time distinction in debt reporting. A D11 design gap can be boundedly resolved while its runtime obligations remain pending. A frozen source record can still show a forward obligation while a downstream accepted propagation record documents later completion. Show the link; do not rewrite the source or count completed propagation as missing runtime execution.

The eighteen source obligation nodes are not automatically eighteen pending runtime obligations. Use the already reviewed P9-1.3 routing rather than inventing a new count-based completion rule.

Unknown claim identifiers should remain unknown. Do not fuzzy-match them into nearby accepted claims to suppress diagnostics.

## 8. Prove that the real entry point ran the successor

A unit test of the successor function is necessary but not sufficient to close normal-entry routing.

### Minimum end-to-end evidence

1. Capture the original normal-entry phase-envelope failure on its stated baseline or retain the already bound reproduction as historical evidence.
2. Run the real normal entry point on the authorized present review tree.
3. Record which historical validator and successor validator were selected, their code identities, and their evaluated subjects.
4. Compare dedicated and normal-entry structured conclusions.
5. Mutate a protected input in an isolated tree and rerun the normal entry point; verify it rejects for the intended reason.

A wrapper must not print a new pass marker while returning a cached historical result, skipping the successor, or catching its failure.

For each negative test, prove the intended check was reached. A forged-authority test rejected because the temporary checkout is missing Git metadata has not tested forged authority. Retain the rejection category and relevant verifier trace, not just nonzero exit status.

Use paired near-neighbor cases: the same proposed file should fail without authorization and pass under a valid simulated authorization with unchanged policy. This tests both over-permission and over-rejection.

Full API/notebook/browser projection verification remains P9-1.8. At P9-1.6, explicitly identify affected surfaces and leave their pending checks visible.

## 9. Staleness, caching, and verification side effects

### Stale result pressure

Run a valid check, then change one of the following without changing the command name:

- an authority record;
- a frozen source member;
- an evaluated review input;
- the dispatcher/verifier implementation;
- a scope policy;
- the relevant current-tree manifest.

An old report must not authorize the new tree. Either invalidate/recompute or report the mismatch. Bind caches to the actual evaluated inputs; branch name and last success are not enough.

### TOCTOU pressure

If an input changes between manifest capture and verification completion, revalidate the final subject or decline current-tree attestation. A result about the earlier snapshot cannot silently become a claim about the later bytes.

### Side-effect boundary

Compare protected sources and governance state before and after both passing and failing verification. Check that the run did not:

- mark an iteration or gate accepted;
- rewrite historical claim/support statuses;
- refresh frozen baselines to match current files;
- regenerate an accepted release;
- remove or rename unauthorized work;
- populate runtime evidence or capabilities by implication.

Authorized diagnostic files and disposable caches may be written to declared locations. That is not the same as mutation of governed authority.

## 10. Three combined outlier tests

Run these after simpler one-fault cases. They expose errors that a collection of isolated unit tests can miss.

### A. Mixed legitimate and illegitimate changes

Start with a valid authorized review package. Add a correctly scoped verifier change, then alter one old-model source byte.

Expected: current-tree rejection identifies the protected-source violation. The legitimate addition does not neutralize it.

### B. Self-consistent but unauthorized promotion

Change the candidate gate to claim runtime permission, add the planned V4 source, and regenerate every candidate-controlled digest.

Expected: rejection at the accepted authorization-chain boundary. Internal hash consistency does not supply acceptance.

### C. Green history, stale current report, valid counters

Keep the historical release valid and all population counts unchanged. Change one support disposition or substitute one compatibility ID after a prior successful run.

Expected: semantic/source identity comparison or staleness validation detects the drift. Historical success and matching totals do not conceal it.

For combined faults, require detection of the forbidden condition and absence of promotion. Do not overconstrain which error appears first unless the accepted policy defines error precedence.

## 11. Reporting boundaries and closure language

A useful report presents separate conclusions for:

```text
historical release validation
historical auditor validation
current-tree identity and scope
successor authority-chain validation
normal-entry routing
claim/support/debt preservation
P9-1.7 adversarial verification status
P9-1.8 surface-reconciliation status
current runtime authorization
accepted generic support set
admitted specialization support sets
```

Before P9-1.9 acceptance, the expected authority/support boundaries remain:

```text
P9-G1: pending
runtime_authorized: false
accepted_generic_runtime_support: []
admitted_specialization_support_sets: []
```

These values describe this phase state, not a permanent rule that would invalidate a properly accepted future successor.

Safe conclusion after the scoped P9-1.6 work:

> The normal entry point selects and executes the successor verifier for the bound Phase-9 review tree while preserving the frozen historical validation. The result establishes verifier routing and review-tree admissibility within the tested scope. It grants no implementation authority, runtime support, conformance, or stronger scientific support.

If adversarial P9-1.7 or affected-surface P9-1.8 checks remain pending, name those remaining conditions on P9-TOOL-001 closure. The checklist both assigns its repair to P9-1.6 and keeps the normal-entry issue held until the applicable P9-1.6–1.8 verification completes; do not collapse those distinct completion claims.

## 12. Evidence to retain for subsequent artifact audit

Retain the exact successor verifier and dispatcher changes, the preparation authorization and scope, bound historical/current inputs, a machine-readable test matrix, actual normal-entry and dedicated-command logs, and before/after protected-file identities.

For every pressure case include:

```text
case ID
base fixture/input identity
mutation or hypothetical successor
expected policy decision
actual decision and reason
which check was reached
command/exit status
verifier and dispatcher identities
source tree/dirty-input identity
authority/release identities
protected pre/post state comparison
evidence kind
review disposition
```

This is verification-tool evidence. It is neither V4 numerical runtime evidence nor reviewer acceptance of P9-G1.

## 13. Priority summary

The highest-value checks are:

1. no broad fallback that converts historical failure into success;
2. no self-authorized runtime promotion, even after rehashing;
3. correct evaluation of historical and current subjects separately;
4. exact mutation scope, including authorized uncommitted work and unauthorized committed work;
5. unchanged support semantics despite unchanged population counts;
6. real normal-entry execution and attributable negative results;
7. no stale result, side effect, or status projection that overstates what passed.

P9-1.6 succeeds when the verifier asks the right question about the right bytes under the right authority—not merely when its command turns green.
