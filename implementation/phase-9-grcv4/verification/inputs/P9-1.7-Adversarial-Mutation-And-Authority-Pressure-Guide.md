# P9-1.7 — Adversarial Mutation and Authority Verification Pressure Guide

**Date:** 2026-09-05
**Role:** prospective guidance for independently reviewed leaf P9-1.7
**Scope:** challenge the successor verifier and actual normal-entry route prepared in P9-1.6
**Authority effect:** none; no P9-G1 acceptance, runtime permission, support promotion, or scientific debt discharge
**Evidence status:** proposed tests only; this guide does not report executions of a submitted P9-1.6/1.7 implementation

## 1. What this leaf must establish

The checklist assigns P9-1.7 both rejection and admission duties: reject unauthorized paths, modified frozen bytes, and stale/forged authority; admit legitimate planning and later explicitly authorized V4 additions in their respective states. P9-1.8 handles affected tool-facing surfaces, and P9-1.9 remains the separate acceptance/authorization step. [S1, S2]

The central question is:

> Does the successor route accept exactly the reviewed changes its authority permits, reject or withhold attestation when necessary, and preserve the distinction between verification success and permission to implement?

A reject-everything verifier is not correct. Neither is a verifier that accepts everything under a V4-looking directory. This leaf needs paired positive and negative cases, not only a large rejection count.

This guide proposes concrete tests for the source requirements. Its probe labels, reporting fields, and batching are local recommendations, not new normative schemas or mandatory project IDs. Use existing accepted dispositions where available. A gap in the verification contract should be resolved through its bounded review, not silently filled by an implementation-specific default.

## 2. Entry: identify what is being tested before mutating it

Bind the exact P9-1.6 candidate verifier, normal-entry dispatcher, relevant helper imports, accepted release, historical baseline, current input manifest, scope policy, and trust anchor. If P9-1.6 is still under review, label its status accurately; running tests does not turn it into an accepted predecessor.

Prepare a known-valid isolated baseline and first show that its authorized review case reaches the expected checks and passes. Keep the base manifest, proposed mutation, expected decision, and decisive source rule separate from the implementation being tested.

The prior P9-1.4/1.5 execution record explicitly describes its seven negatives as review-data checks rather than mutation-policy tests. Reuse their concepts, but do not count them as P9-1.7 execution evidence. [S4, S6]

### Protect the live checkout

Perform adversarial source changes, fabricated future authorities, and deliberate checker breakage in disposable repositories or isolated bound file trees. Do not add hypothetical runtime permissions to the real Phase-9 gate. Review-tool test paths also need the current leaf's explicit mutation authorization; the proposed later V4 runtime `tests/` paths are not blanket permission now. [S1, S3]

### Bound the threat model

The useful scope here is a candidate change attempting to defeat the declared checks while a separately identified accepted baseline and verifier invocation remain trusted. It is not a claim of resistance to an attacker controlling the operating system, every trust anchor, and the test harness simultaneously.

A fixture can establish simulated acceptance through its own isolated trusted root. The distinction must be explicit: an accepted fixture successor comes from that root; a forged candidate successor tries to manufacture permission below it. Do not make the only positive test depend on disabling authority checks.

## 3. State-and-permission matrix

Freeze a small expected-decision matrix before the run. The following is a recommended minimum structure.

| Case | Setup | Expected interpretation |
| --- | --- | --- |
| Review-positive | Valid explicitly authorized review additions; no runtime grant | Current review scope admitted; runtime still unauthorized. |
| Premature source | Add the proposed `grc_v4.py` before P9-G1 | Reject unauthorized runtime source even though the filename is planned. |
| Premature test | Add future V4 runtime tests before their grant | Reject for the same authority boundary; a test file is not automatically exempt. |
| Future-positive | Same addition under a separately trusted simulated accepted P9-G1 | Admit only the exact simulated scope; no live gate promotion. |
| Frozen-byte mutation | Change a protected source, specification, decision, auditor, or release member | Reject integrity or scope; historical success does not certify changed current bytes. |
| Additive-path misuse | An authorized integration edit also rebinds an old export or changes unrelated dependencies | Withhold acceptance of the unauthorized content; filename allowance is insufficient. |
| Unauthorized committed change | Commit a forbidden modification and leave a clean worktree | Reject based on the accepted-to-current comparison, not merely the dirty diff. |
| Authorized dirty review | Keep an authorized hash-bound review package uncommitted | Do not reject solely for Git status; validate exact bytes and permission. |
| Missing historical input | Historical commit, dependency, or member unavailable | Historical check incomplete/unverifiable, not passed and not a scientific refutation. |
| Rehashed forged grant | Alter authority and recompute all candidate-controlled hashes | No promotion without the accepted trust chain. |
| Wrong context | Valid-looking grant for another release, baseline, scope, or predecessor | Reject or explicitly hold; similarity of names is not authority. |
| Mixed change | One legitimate addition plus one forbidden change | Legitimate work cannot conceal the forbidden change. |

"Admit" means that the mutation is permitted under the named authority. It does not certify the new runtime's equations, semantics, or conformance. For the separately reviewable integration paths, preserve any substantive diff-review requirement; a mechanical path checker cannot alone prove all behavior unchanged. [S4, S5]

## 4. Mutation coverage beyond ordinary file edits

### 4.1 Enumerate the complete evaluated change scope

Exercise committed changes since the accepted baseline, staged changes, unstaged changes, deletions, renames, and relevant untracked executable helpers. A renamed protected file is still a protected-file deletion plus an addition; it must not become harmless because its new basename looks permitted.

Also test a file-type change, such as an allowed-looking path replaced by a symlink. Normalize paths under the declared policy and check their resolved targets. A symlink to protected or outside material cannot acquire permission merely from its visible name.

Untracked build output and unrelated work require explicit scope handling. Not every temporary file is scientific input, but no runtime-importable helper or authority input may be ignored only because it is untracked. Report exclusions and their reasons. Do not delete unrelated work to make verification succeed.

### 4.2 Probe common bypasses

Recommended cases include:

- a protected path referenced through `..` or a symlink;
- an untracked module shadowing a historical checker dependency;
- staged authorized content but different unstaged file bytes consumed at execution;
- an allowed directory prefix with a sibling name that only resembles it;
- a deleted historical boundary paired with a candidate replacement manifest;
- a permissions or executable-mode change where the current policy treats it as load-bearing.

Cross-platform path forms should be tested only within the declared platform/portability envelope. Unsupported representations should produce narrow diagnostics rather than an invented universal pathname policy.

### 4.3 Test what actually executes

Bind the imported verifier/helpers and selected data, not only the launch script. A historical checker with current dependencies is not automatically a reconstruction of historical verification. Run from a different working directory to expose accidental relative-path imports where the tool promises that invocation mode.

## 5. Authority, forgery, and staleness pressure

### 5.1 Candidate records cannot grant themselves trust

Start with valid review authority, flip `implementation_authorized`, add proposed runtime code, and recompute candidate-owned hashes. The test should still withhold the claimed runtime permission. Also test an unchanged gate ID with altered predecessor bytes, a cyclic predecessor chain, a missing acceptance record, and conflicting candidate successors.

Do not introduce a new signature system solely for this leaf. Test the trust and acceptance model the project actually declares. If that model does not distinguish candidate content from accepted permission, record the exact missing proposition and hold that part of the verification contract.

### 5.2 Old false flags and new false grants are different

Historical `implementation_authorized=false` remains true of its historical gate. It must not veto a valid later successor in the simulated future-positive case. Conversely, a new true flag without the accepted successor must not override it. The expected output preserves both subjects and times rather than resolving them by Boolean OR or AND. [S1, S3]

### 5.3 Cached success is evidence about one subject

After a passing run, separately change an authority record, scope policy, helper, protected source, or evaluated input. Rerun through the normal entry point. The old report cannot attest the changed tree merely because the branch and release label are unchanged.

Test an input change during verification. Either verify an immutable captured snapshot and state that subject accurately, or detect the change and decline current-tree attestation. Do not require one particular locking implementation; require that the conclusion and evaluated bytes agree.

Missing material should be reported as unavailable or unverifiable when that is what happened. A missing authority cannot permit runtime work, but it is not automatically proof of malicious forgery.

## 6. Claim drift without count drift

Preservation tests must compare source-bound identities and semantics, not just the 41/80/183/10/40 headlines.

The P9-1.5 review specifically preserves the 152 D10.2 support dispositions `indeterminate_requires_review` while retaining accepted specifications as implementation authority. Neither side should be "fixed" into another meaning. [S4]

Recommended mutations, each applied alone to an isolated copy:

| Mutation | Required pressure result |
| --- | --- |
| Conditional claim becomes normative | Detect an unauthorized claim-class change. |
| `indeterminate_requires_review` becomes supported | Detect unsupported strengthening of a support association. |
| Candidate C optional contract becomes universal | Detect loss of candidate/profile scope. |
| GRC9-only contract becomes graph-generic | Detect specialization leakage. |
| One forty-cell compatibility row duplicates another | Detect exact set/key mismatch despite unchanged count. |
| Planned C_OS becomes accepted runtime support | Detect promotion without the required exact identity/evidence gate. |
| One evidence alias is counted as a second independent result | Detect duplicate credit, while still allowing the same result to be referenced by two consumers. |
| Unimplemented obligation becomes nonapplicable without source-backed scope | Retain a pending obligation/hold rather than deleting it. |
| Deferred RG2b status becomes scientifically rejected | Preserve the distinction between scheduling and scientific disposition. |

Keep old obligation status and later accepted propagation completion as separate linked facts. Use the reviewed P9-1.3 routing; do not invent a new pending-obligation total. Unknown IDs should remain unknown, not be fuzzy-matched to an accepted neighbor. [S1]

Exact baseline hash checks may already detect a source mutation. If a semantic-projection checker is also claimed, test it with a controlled changed projection after source admission so its semantic comparison is actually exercised. A hash mismatch alone proves integrity detection, not execution of every downstream semantic rule.

## 7. Show that the tests discriminate

### 7.1 Three outcomes, not one green flag

Record separately:

1. **candidate decision:** was the mutated tree admitted, rejected, or not verifiable?;
2. **test assertion:** did that decision match the independently specified expectation?;
3. **project effect:** did this run grant permission or close a gate? Normally no.

For a successful negative test:

```text
candidate tree: rejected
negative-test assertion: passed
runtime permission: not granted by this test
```

An exception caused by absent Git metadata is not a successful forged-authority rejection. A timeout is not a passing protected-byte test. Preserve the decisive rule or trace showing that the intended protection was reached.

### 7.2 Positive/negative pairs

At minimum, pair premature source with a valid simulated future source grant, and frozen-file corruption with unchanged frozen files plus a legitimate review addition. These pairs detect both accept-all and reject-all implementations.

Where practical, deliberately break one protection in a disposable checker copy and confirm that its corresponding test fails. Useful mutations are suppressing frozen-byte comparison, accepting all new paths, ignoring successor digests, or swallowing a child checker failure. Keep those deliberately broken checkers outside accepted or production paths and out of the live authority chain.

### 7.3 Avoid self-grading

Do not compute expected permission by calling the same scope predicate that computes actual permission. A helper can prepare fixtures, but expected decisions need a separately reviewed rule/case table. The existing ownership review already prohibits production calculating its own test oracle. [S4, S5]

### 7.4 Exercise the normal route

Run the high-value cases through the real normal command, not only the successor function. Bind exit status, structured result, selected verifier identities, and relevant trace. If execution stops early on one valid blocking condition, do not claim downstream checks also executed. Test those in separate single-fault cases.

## 8. Three combined outliers worth keeping

**Allowed addition plus protected corruption.** The authorized change remains recognized, but whole-scope acceptance fails for the protected mutation.

**Self-consistent forged successor plus runtime addition.** Candidate hashes agree, but acceptance provenance does not. No runtime permission follows.

**Valid baseline, then stale report reuse.** Run once, alter one support scope or authority input without changing counts, and run again. The old result cannot certify the changed subject.

Add a fourth at the P9-1.7/P9-1.8 boundary: a negative test correctly rejects its candidate, but a consumer renders the harness's passed assertion as "tree verified." P9-1.7 supplies the result fixture; P9-1.8 checks the projection.

## 9. Evidence package and bounded completion

For each probe retain the base identity, exact mutation/diff, authority/trust context, expected decision and source rationale, actual decision, decisive check/trace, exit status, assertion outcome, protected pre/post manifests, run identity, and residual limitation. Keep failed runs and subsequent fixes distinguishable.

Separate a verifier execution record from a V4 model's runtime lifecycle receipt. Governance-tool execution is not evidence that C_OS or GRC9V4 ran. [S2, S6]

At closeout reconcile named probe families, not just total assertions. Summarize valid/invalid admission pairs, authority attacks, frozen-byte mutations, semantic drift, normal-entry behavior, side effects, and untested cases. A finite matrix is bounded adversarial evidence, not a universal security proof.

P9-1.7 can earn:

> Under the named verifier, trust model, and input envelope, the reviewed positive and negative cases produce the expected scoped permission and preservation decisions, including normal-entry execution.

It does not earn P9-1.8 surface reconciliation, P9-G1 acceptance, runtime permission, conformance of a proposed V4 module, or stronger scientific support. Its completed evidence becomes an input to the later review. [S2, S3]

## 10. Suggested execution batches

Preserve P9-1.7 as the parent leaf or register children under the already permitted child-splitting rule:

1. baseline and permission-state pairs;
2. file scope, frozen integrity, trust/forgery, and semantic drift;
3. stale inputs, normal-command integration, fault sensitivity, and final evidence reconciliation.

Each batch retains its own result. A failed shared authority test blocks dependent acceptance; an optional unexecuted platform probe remains a named limitation rather than evidence that every other check failed. No number of probe passes automatically accepts the enclosing tranche.
