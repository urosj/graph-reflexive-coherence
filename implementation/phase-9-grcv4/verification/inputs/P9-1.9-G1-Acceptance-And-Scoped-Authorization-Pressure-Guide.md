# P9-1.9 — P9-G1 Acceptance and Scoped Authorization Pressure Guide

**Date:** 2026-09-05
**Role:** prospective guidance for independently reviewed leaf P9-1.9
**Scope:** reconcile Tranche-1 review evidence and record the accepted, hash-bound P9-G1 successor before V4 runtime implementation
**Authority effect of this guide:** none; no gate acceptance, permission grant, specification change, or runtime conformance claim
**Evidence status:** recommended pressure tests and acceptance procedure; not an audit of submitted P9-1.6–1.9 execution artifacts

## 1. The distinct question for P9-1.9

The checklist assigns P9-1.9 the recording of accepted P9-G1 successor authority with exact mutation scope and release bindings before runtime work starts. The plan requires this successor to permit concrete V4 source/test additions and necessary additive integration while protecting the accepted release and old semantics. [S1, S2]

The central question is:

> Has the actual acceptance process approved this exact reviewed package and a sufficiently precise forward work scope, with a verifier that both permits that work and preserves all remaining gates and nonclaims?

P9-1.6 constructs the verification route. P9-1.7 pressures its decisions. P9-1.8 pressures their presentation. P9-1.9 is where a genuine acceptance decision can become an effective implementation authorization. It is therefore not just another passing tool run.

Two mistakes are equally important:

**False permission:** green checks, a planning record, an assistant recommendation, or a self-authored flag is treated as accepted runtime authority.

**False prohibition:** a genuinely accepted successor still cannot permit its specified V4 work because a historical `implementation_authorized=false` or blanket old-tree comparison remains the controlling decision.

The correct result is neither perpetual refusal nor blanket permission. It is effective, bounded permission under the approved dependencies.

### Source versus recommendation

The source obligations are identified by [S1]–[S8] below. The proposed pressure labels, reporting fields, logical model, and publication procedure in this guide are engineering recommendations for satisfying those obligations. They are not new project schemas, cryptographic-signature requirements, scientific contracts, or automatic additions to the gate policy. Reuse the actual accepted successor-verification representation where it already provides these semantics.

No final P9-1.6, P9-1.7, P9-1.8, or P9-1.9 execution package is reviewed here. Earlier supplied records describe their own historical states; they are not proof that later corrections or acceptances have occurred. Bind the actual final versions when performing this leaf.

## 2. Keep four decisions distinct

| Decision | What it establishes | What it does not establish |
| --- | --- | --- |
| Review evidence is sufficient | Named technical prerequisites have the required disposition for the bound input package. | An actor has actually granted implementation authority. |
| P9-G1 is accepted | The designated acceptance process approves the exact successor proposal. | Every planned file, candidate, or future leaf may execute immediately. |
| A concrete work item is permitted now | The accepted scope covers its operations and paths, and its entry dependencies are satisfied. | Its implementation is correct or conformant. |
| Runtime/profile conformance is accepted | Later applicable runtime evidence has passed its own review for exact identities and domains. | Other profiles, broader domains, or scientific claims are established. |

The supplied opening deliberately separates planning activation from implementation acceptance and leaves generic and specialization support sets empty. The profile gates and the execution-granularity rules must survive P9-G1. [S2, S3]

At the intended first G1 transition, the relevant outcome is:

```text
P9-G1 acceptance:
  accepted, if the real decision and all required bindings are present

V4 implementation permission:
  enabled within the approved scope and entry conditions

accepted generic runtime support:
  unchanged; empty at this first authorization

admitted specialization support sets:
  unchanged; G3 is not granted by G1

runtime conformance / scientific debt discharge:
  none earned by this acceptance action
```

Here, permission to perform runtime implementation and tests is not a claim that a runtime already exists or has been certified.

### Pressure cases

**Pending review hidden by completion.** A leaf says its engineering work is complete but its required acceptance remains pending. G1 must not infer the missing acceptance. The designated decision may explicitly accept that exact leaf at the gate, if the process allows it, but the decision must be recorded.

**Mixed revisions.** A P9-1.7 result tests verifier A, while the candidate G1 relies on verifier B changed during P9-1.8. Hold the affected assurance until its tests run against B; do not rerun unrelated science.

**Superseded dependency record.** A support register is corrected after review. Bind the accepted correction and its relation to the earlier record, rather than silently resolving a mutable path to whichever bytes now exist.

**Missing evidence disguised as nonapplicability.** An affected consumer or required adversarial category cannot run. Record the limitation and its gate effect. Only genuinely inapplicable scope receives an explicit nonapplicability rationale.

### P9-TOOL-001 closure

Reconcile the normal route, adversarial assurance, and affected-surface evidence together. Preserve the original historical failure. A route-only pass does not establish the other leaves; an old failure does not prove the corrected current route still fails. The current issue disposition should cite the exact successor results on which it rests. [S1–S3]

## 4. Separate G1 blockers from future runtime holds

The purpose of G1 is to authorize implementation against a complete contract, not to require the implementation before permission is granted.

| Condition | Appropriate G1 treatment |
| --- | --- |
| Required authority chain, verifier result, or protected-input identity cannot be verified | Hold the affected acceptance/grant. |
| Mutation scope is ambiguous or would permit frozen specification changes | Correct before activation. |
| A required P9-1.7 category failed or an affected P9-1.8 projection misstates permission | Hold; do not relabel as ordinary runtime debt. |
| Candidate A runtime numerics, RG2b certification, or child-completion execution is not yet available | Retain the named future hold; do not automatically block the first generic implementation route. |
| Full V4 lifecycle or forty legacy-delegate executions do not yet exist | Retain later conformance obligations; do not require them before G1. |
| A proposed dependency package is not installed yet | Bind the authorized preparation/review path; do not claim the package was validated or require unauthorized installation first. |
| A real source/specification contradiction is exposed | Record the exact proposition and route it under the source policy; G1 cannot rewrite the frozen contract. |

The plan already routes remaining work and permits independently reviewed profile paths. The gate should preserve that scheduling rather than adding an all-ten-profile or all-tranche barrier. [S1, S2, S4]

A bounded acceptance must name its scope. It must not turn “future work remains” into unrestricted permission, nor turn an unrelated future hold into a veto over every ready leaf.

### No self-granting acceptance

Prepare a reviewable candidate proposal, validate it without activating it, and record the real acceptance decision against its exact identity. Generating a proposal or running its checks must leave live implementation permission unchanged until the declared acceptance condition is met.

An audit recommendation is evidence for the decision, not a substitute for the user's or designated approver's acceptance. A user instruction to prepare or check P9-1.9 is not automatically an instruction to claim the gate has already been accepted. Conversely, an explicit acceptance of the exact package should not be ignored merely because an older record still says false.

A digest authenticates correspondence with bytes only relative to the trusted acceptance chain. Rehashing a self-edited permission flag cannot supply that acceptance.

Use the already reviewed trust model; this guide does not prescribe a new certificate authority, signing infrastructure, or federation-wide authority.

### No circular digest construction

Keep the candidate payload, validation evidence, acceptance decision, and post-activation verification direction explicit. An acceptance payload must not hash its own final digest or require the commit hash of the commit that contains that payload. A post-activation report may refer to the accepted gate, but must not become the retroactive prerequisite that created that gate.

Reuse existing accepted serialization and successor-record rules. If the gate representation leaves an ordering unresolved, close that narrow engineering point before activation rather than inventing an implicit exception.

## 6. Specify usable forward scope without blanket permission

The scope should answer, for every proposed mutation:

```text
What path or controlled path grammar?
What operation: create, modify, rename, or delete?
What content/purpose boundary?
Which leaf or profile path owns it?
Which prerequisites must already hold?
What review or regression follows?
What remains forbidden?
```

The P9-1.5 ownership review proposes V4-local modules, tests, a separate harness/oracle, and evidence storage. It separately identifies only two existing integration files: `src/pygrc/models/__init__.py` and `pyproject.toml`. These are recommendations until accepted, not blanket edit authority. [S6, S7]

### Recommended scope distinctions

| Surface | Scope to settle explicitly |
| --- | --- |
| New V4 generic modules and their tests | Exact reviewed additions and permitted subsequent edits under their owning leaves. |
| V4 harness and independent reference oracles | Creation and evolution outside frozen vectors; production must not import them. |
| Runtime evidence directories | Declared run-path grammar, provenance requirements, and preservation of failures; not a writable escape into governance inputs. |
| Shared model exports | Only reviewed additive V4 exports; no rebinding old names or requiring new dependencies for legacy imports. |
| Dependency declarations | Exact approved V4-extra change or a declared later review condition; no permission to upgrade unrelated packages. |
| Packaging resources, lockfiles, or additional files found necessary | Explicitly add to scoped review before mutation; do not assume permission from being a build by-product. |
| GRC9V4-specific implementation | Conditional on the consumed generic G2 and reviewed G3 set; G1 alone is insufficient. |
| Governance/verifier changes after acceptance | Separate controlled amendment/review; runtime permission cannot let code weaken its own admission policy. |
| Accepted release, specs, paper/proposal, D10/D11, historical auditor/boundaries, protected legacy sources/tests | Remain protected according to their recorded contracts. |

A path allowance is not semantic acceptance. An integration file can be in scope while a particular diff to it is not.

Do not classify every new repository path as frozen merely because the baseline lists existing files. The supplied baseline explicitly distinguishes its immutable members from legitimate future V4 additions. [S7]

### Baseline versus future tree

The acceptance evidence concerns a fixed reviewed baseline. The permission grant is intended to permit future changes relative to that baseline. Those are different subjects.

Do not require the entire future implementation tree to equal the preimplementation tree hash: that would reject every authorized addition. Instead verify the bound baseline and protected inputs, then evaluate the actual descendant change set under the accepted mutation and dependency rules.

An altered authority prerequisite or release is not an ordinary permitted code delta. It requires explicit revalidation or successor acceptance. An authorized implementation edit does not, by itself, erase the historical validity of G1, although it must pass the checks applicable to its own work item.

## 7. Do not let G1 bypass leaf and specialization gates

The plan makes tranches organizational and individual leaves independently executable/reviewable. G2 accepts exact generic runtime scopes, while G3 admits specialization work for an already accepted generic support set. [S1–S4]

Use the following as an illustrative permission model, not a new scientific equation:

```text
work_permitted_now =
    accepted successor applies to this release and baseline
    AND requested mutation is inside its declared scope
    AND the owning leaf's entry dependencies hold
    AND all applicable protected-input and review conditions hold
```

Consequences:

**Foundation:** once G1 is genuinely active, the ready foundation leaves may proceed according to the final dependency register. In the supplied reviewed schedule, P9-2.1 and P9-2.2 have G1 as their external prerequisite; the final accepted revision controls. [S5]

**Later generic leaves:** listing `grc_v4_candidate_a.py` or all realizations in the ownership plan does not mean their implementation leaves are immediately ready. Preserve the chosen first-route dependencies and exact future activation policy.

**Specialization:** naming `grc_9_v4_expansion.py` in the module inventory does not make GRC9 work legal before the relevant G2/G3 admission. G1 must not make a path-only allowlist bypass this gate.

**Support:** permission to write a C_OS runtime must not populate the accepted C_OS runtime-support set. That requires the later full fixture/lifecycle acceptance. Likewise, a profile template is not an admitted or executed complete profile.

There is no requirement here to issue a new human approval for every statement or helper function. Use the project's accepted leaf/batch process; do not introduce unplanned bureaucracy or remove the existing per-leaf review boundary.

## 8. Highest-value test: the real permission transition

Test this sequence using the normal entry point. Before real acceptance, use isolated fixtures with their own explicit trusted acceptance roots; never let hypothetical future gates enter the live authority resolver.

| State and attempt | Expected result |
| --- | --- |
| Review-only authority; create a named future V4 runtime module | Rejected as premature. |
| Same review tree; prepare a G1 proposal and run validation | Proposal may validate, but implementation permission remains unchanged. |
| Candidate gate merely sets accepted flags and rehashes itself | No accepted permission without the declared acceptance reference/trust chain. |
| Valid independently accepted G1; perform the same in-scope, dependency-ready source/test addition | Mutation admitted within its scope. No runtime conformance follows. |
| Valid G1; modify a frozen V3 or accepted-specification byte | Rejected. |
| Valid G1; create an out-of-scope helper or perform an unrelated dependency edit | Rejected or held for the required scope amendment. |
| Valid G1; create GRC9-specific implementation before its G3 entry | Not permitted under the supplied dependency policy. |
| Valid G1; automatically mark G2[C_OS] accepted or advertise all ten families | Rejected as an unsupported gate/claim promotion. |
| Historical release auditor still reports its recorded implementation flag as false | Preserve the historical result; current permission is separately resolved from valid G1. |

The permitted addition should be a minimal policy probe in a disposable copy, not runtime implementation smuggled into P9-1.9. Its pass establishes permission discrimination, not correctness of the prospective module.

After actual acceptance, make a read-only effective-authority check through the live normal route and retain its output. It should recognize the actual new grant, while leaving runtime support and future gate state unchanged.

## 9. Outlier matrix for the acceptance record itself

The following cases supplement, rather than replace, the broader P9-1.7 matrix. Reuse its reviewed harness and evidence where applicable.

| Probe | Risk | Expected interpretation |
| --- | --- | --- |
| A1: All checks green; no actual acceptance decision | Technical readiness mistaken for permission | Candidate remains pending; no grant. |
| A2: Acceptance refers to an earlier proposal digest | Scope changed after approval | No permission for the changed proposal; refresh the affected acceptance. |
| A3: One referenced P9-1.8 output is absent | Missing evidence converted to pass | Hold any conclusion that requires it; preserve explicit applicability. |
| A4: Same branch name, different release or baseline | Branch label used as authority | Reject mismatched binding. |
| A5: Clean Git worktree containing an earlier unauthorized committed edit | Cleanliness substituted for change-scope verification | Detect baseline-to-current violation. |
| A6: Exact authorized review package remains uncommitted | Dirty worktree treated as automatically invalid | Accept or hold according to the explicit evidence/publication policy, not dirtiness alone. |
| A7: Runtime files already existed before G1 | New grant used retroactively | Record the boundary violation; do not backdate authority or claim those edits were authorized. |
| A8: Two conflicting accepted-looking G1 records | Latest filename/timestamp wins | Resolve under an explicit successor relation; otherwise withhold ambiguous permission. |
| A9: Verification code changes after its pressure tests | Untested verifier accepted through old report | Rerun affected assurances for the actual code. |
| A10: Generated file asks for unrestricted `src/` access | Minimal scope becomes blanket grant | Reject widening or obtain a specific reviewed scope revision. |
| A11: Evidence path escapes into protected inputs | Test output permissions become mutation bypass | Reject scope escape. |
| A12: Candidate files change between review and publication | Accepted digest no longer names published subject | Abort activation of the changed subject or require revalidation. |
| A13: Re-run the identical accepted publication | Duplicate/conflicting gate generation | Recognize the same decision without creating new authority, new acceptance credit, or duplicate support. |
| A14: Simulated acceptance fixture is copied into live discovery | Test authority becomes real authority | Reject under the live trust chain. |
| A15: Accepted authorization loses a prerequisite or is superseded by a narrowing decision | Old permission remains cached | Preserve historical acceptance but do not issue current permission unsupported by the effective chain. |
| A16: All G1 requirements hold but runtime vectors are still pending | Premature demand for G2 before G1 | Permit reviewed implementation work; retain the runtime holds. |

For A7, preserve evidence of the boundary problem. The authorized process must decide how to restore a legitimate preimplementation baseline or separately review the situation. A flag change alone is not remediation.

For A15, this guide does not invent a revocation protocol. If the project supports withdrawal/narrowing, its accepted semantics control. If effective authority becomes unresolved, report that precisely rather than selecting an older permissive record by fallback.

## 10. Preserve claim and debt meaning at the transition

The source population and reviewed architecture do not become stronger merely because implementation is authorized. The P9-1.5 review expressly retains the 152 D10.2 `indeterminate_requires_review` associations while continuing to use accepted specifications as implementation authority. [S6, S7]

Check the transition's before/after projection:

```text
accepted scientific claims and their classes:
  unchanged by G1

D11-C and D11-G9 bounded design resolutions:
  unchanged by G1

forensic support dispositions:
  unchanged by G1

runtime evidence obligations:
  routed, not discharged by permission

accepted exact generic/runtime identities:
  unchanged by G1

specialization-admitted consumed sets:
  unchanged by G1

legacy compatibility cells:
  remain independently tracked and unexecuted unless their own evidence exists
```

Compare exact identifiers, classes, scopes, and dispositions, not only 41/80/183/10/40 counts. Those counts concern different populations; they are not a count of tests passed.

A design-level resolution can coexist with runtime obligations. Historical forward-status records can coexist with later accepted propagation completion. Use P9-1.3's reviewed routing rather than rewriting the frozen sources or guessing outstanding counts from subtraction. [S1, S3]

An acknowledged review limitation is not automatically a G1 blocker, and an acceptance prerequisite is not safely deferred merely by naming it a debt. Its effect must match the contract and the proposed scope.

## 11. Publication and post-acceptance freshness

The supplied source requires a new hash-bound successor, not modification of the historical acceptance files. [S1, S3]

A practical sequence to review is:

```text
assemble final prerequisite evidence and scope proposal
    -> validate the exact candidate package without activating it
    -> obtain/record the actual acceptance of that package
    -> publish the accepted successor under the authorized governance scope
    -> verify the exact published bindings through the normal entry point
    -> expose the next dependency-ready implementation leaves
```

The files needed to prepare and publish P9-1.9 require the current review/governance authority. They cannot be justified solely by the runtime permission that they are about to create. State that small publication scope before writing them.

Keep current summaries as projections of the accepted record, not independent permission stores. A partially written acceptance package, stale API cache, or updated checklist alone must not activate authority. Publication should expose either the complete valid binding set or an explicit incomplete/pending state.

Do not solve self-reference by excluding arbitrary governance files from every check. Identify each payload and its exclusions narrowly. A later commit/tag may index an already fixed acceptance package without being part of the package's own circular preimage.

A clean-checkout replay is useful. The supplied records also allow exact hash-bound uncommitted review packages; do not add a blanket committed-only requirement unless separately chosen. In either case, bind the actual evaluated bytes and the actual acceptance reference. [S8]

### Change classification after acceptance

- **Permitted runtime edit:** evaluate it against baseline, scope, and leaf requirements. It is not automatic invalidation of G1.
- **Changed prerequisite, verifier, or permission rule:** revalidate the affected assurances and obtain the required successor decision; do not silently update stored hashes.
- **New scientific equation or changed accepted specification:** use the declared scientific/specification successor route, not a G1 amendment disguised as packaging.
- **Changed presentation only:** test that it remains presentation-only; an altered status or claim ceiling is semantic even if in Markdown.

## 12. Carry P9-1.8's fidelity into the newly active state

The preceding surface tests may have exercised a simulated future accepted gate. P9-1.9 should additionally confirm that the actual published gate is presented correctly by the affected real consumers.

The useful output is:

```text
historical release:
  valid for its bound historical subject

current implementation authority:
  accepted G1 identity and exact effective scope

next permitted work:
  only dependency-ready leaves under that scope

runtime support:
  none earned by this gate

remaining G2/G3/G4 requirements:
  visible and unchanged
```

A browser or exported report must not display “GRCV4 implemented” because “implementation authorized” became true. A negative-case harness pass remains a rejection of its candidate, even after real G1 acceptance.

If the actual record representation differs from the one tested in P9-1.8, rerun affected projections. No whole-tool redesign is needed. Unaffected surfaces retain their reviewed nonapplicability decisions. [A3]

Retain the following content, using existing project file formats rather than creating redundant registries:

| Artifact content | Audit purpose |
| --- | --- |
| Per-leaf prerequisite/condition reconciliation | Shows what has been accepted, what is only complete, and what remains a hold. |
| Exact final source/evidence manifest | Prevents stale or mixed package acceptance. |
| G1 candidate scope and actual acceptance reference | Separates recommendation, decision, and permission. |
| Mutation/dependency rule bindings | Makes forward permission executable and bounded. |
| Normal-entry pre- and post-activation results | Demonstrates that the accepted grant is recognized without rewriting history. |
| Targeted permission-transition probe results | Tests both legitimate admission and continuing prohibitions. |

| Leaf execution record and parent reconciliation | Completes P9-1.9 without implying Phase-9/runtime completion. |

A governance acceptance report is not a GRCV4 scientific runtime receipt. Preserve their distinct artifact types and meanings.

For any proposed pressure case not executed, record that fact and its acceptance consequence. Do not turn this guide's test inventory into a claim that all tests have already passed. Equivalent reviewed evidence is reusable by exact reference; additional reports do not manufacture independent executions.

## 14. Suggested closing statement

The following is illustrative wording to use only after the actual acceptance and checks occur:

> P9-G1 is accepted for the bound specification release, reviewed predecessor package, and explicit V4 mutation scope. The named next implementation leaves may proceed subject to their entry dependencies and continuing verification. Historical acceptance records and protected sources remain unchanged. This decision does not accept any runtime profile, admit GRC9V4 specialization ahead of G3, discharge scientific/runtime evidence obligations, or authorize changes to the frozen paper, proposal, specifications, or legacy behavior.

For an incomplete acceptance package, use an equally explicit bounded disposition:

> The G1 candidate package is prepared or technically reviewed, but no effective implementation grant is recorded because the named prerequisite, acceptance reference, or publication binding remains unresolved. Previously accepted source results remain valid within their scopes.

Do not report a completed grant while attaching an unresolved condition required for that same grant. Narrow work scope explicitly only if the actual gate policy permits such an acceptance; do not use conditional language to bypass a mandatory Tranche-1 prerequisite.

### What completion means

```text
P9-1.9:
  accepted successor recorded and its effective scope verified

Tranche 1:
  reconciled as the implementation-review/authorization tranche

Phase 9:
  implementation work begins; not complete

G2, G3, G4 and runtime/scientific claims:
  remain at their independently earned states
```

The goal is a transition that permits real implementation, not one that claims the implementation's results in advance.
