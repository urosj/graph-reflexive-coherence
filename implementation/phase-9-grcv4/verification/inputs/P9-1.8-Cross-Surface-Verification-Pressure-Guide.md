# P9-1.8 — Cross-Surface Verification and Claim-Fidelity Pressure Guide

**Date:** 2026-09-05
**Role:** prospective guidance for independently reviewed leaf P9-1.8
**Scope:** affected tool plan/checklist, normal CLI, API, notebook, browser, and exports
**Authority effect:** none; this leaf communicates and verifies existing conclusions, not P9-G1 acceptance
**Evidence status:** proposed tests only; no API/notebook/browser implementation has been audited by this guide

## 1. What this leaf must establish

P9-1.8 updates the tool plan/checklist and any API, notebook, or browser surfaces affected by successor verification, retaining consistent authority labels. P9-1.9 separately records accepted P9-G1 authority before runtime work. [S1, S2]

The central question is:

> Can every affected consumer present or export the verified result without changing its subject, scope, freshness, authority, evidence kind, or claim ceiling?

The key failure is not only that an interface crashes. It is that a perfectly rendered page reports more than the backend established.

Examples of unacceptable inference:

```text
historical release valid -> current tree valid
review-tree admissible -> implementation authorized
negative test passed -> rejected candidate admitted
all ten families listed -> ten profiles implemented
legacy regressions pass -> V4 disabled compatibility established
cached audit available -> current checkout freshly verified
```

The examples and fields below are advisory test designs. They do not replace accepted API schemas, introduce new scientific status categories, or require creating a browser capability that does not exist.

## 2. Start with a surface applicability inventory

List the actual consumers affected by the P9-1.6 routing change. For each, record its input contract, what it executes or displays, its output/export, and the review owner.

| Surface | Possible role to confirm | Scope discipline |
| --- | --- | --- |
| Normal CLI | Runs historical and successor routes, emits exit/result | Distinguish current verification from child or harness status. |
| Tool API | Runs a verifier or serves a bound report | Say which; transport success is not scientific pass. |
| Notebook | Executes verification or loads previously produced results | Bind cells, inputs, and outputs to the same run. |
| Browser | Live service consumer, local artifact checker, or offline viewer | Do not imply live Git verification when only a snapshot is loaded. |
| Tool plan/checklist | Progress and dependency reporting | Leaf completion does not accept the tranche or P9-G1. |
| JSON/Markdown/download export | Portable report | Keep source identity, limits, and negative-test subject. |
| Documentation/examples | Explain invocation and interpretation | Mark illustrative outputs and historical examples accurately. |

The source phrase is **affected surfaces**. An existing but unaffected path can be marked not applicable with a reason and an unchanged-contract check. Do not rewrite every tool or create a new frontend merely to fill the table. Conversely, an affected surface that cannot be tested remains unverified; it is not silently converted to not applicable.

Freeze the exact P9-1.6/1.7 result versions being projected. If P9-1.8 uncovers a backend defect requiring a patch, rerun the affected P9-1.7 cases against the patched verifier. Presentation tests over an old binary do not validate a new one.

## 3. Preserve a multidimensional result

One bare `PASS` cannot carry the relevant conclusions. Whatever existing representation is used, it should preserve the equivalent of:

```text
operation / run / scenario identity
historical release and historical evaluated subject
current evaluated tree or content-manifest identity
successor authority identity and allowed scope
historical check result
current-scope check result
required checks executed / failed / unavailable
candidate admission decision
test-assertion result, if this is a test report
runtime authorization and its source
accepted exact-profile support set
source support dispositions and pending holds
evidence kind: actual run, historical record, or simulation
```

These are semantic obligations to map into the existing report, not a demand to mint another normative identity system.

If a frontend combines several independently produced results, require their subject/authority identities to agree or show them as separate results. It must not combine a historical pass from one release, a scope pass from another tree, and a true flag from a third record into a synthetic "accepted" state.

Do not discard a whole useful partial result solely because another required check is unavailable. Preserve what was checked, but withhold the overall attestation that needs the missing check.

## 4. Recommended shared scenario corpus

Use reviewed result fixtures from P9-1.7 where available, including raw verifier output and test-harness wrapper. Each affected surface should retain the same decision-relevant content. Formatting, timestamps, or view-only metadata need not be byte-identical across presentations.

| Scenario | Meaning that must survive projection |
| --- | --- |
| Accepted historical release; review tree valid; P9-G1 pending | Review verification can pass while runtime authority remains false. |
| Historical release valid; current protected bytes changed | Historical pass remains historical; current verification fails. |
| Forged or stale successor record | Claimed permission rejected/held, not replaced by a cached historical pass. |
| Required verifier unavailable or interrupted | Could not complete current verification; not a successful skip. |
| Negative mutation rejected as intended | Candidate rejected, test assertion passed, no permission created. |
| Simulated future accepted authority | Clearly simulated fixture scope, never live runtime permission. |
| Old report from a previous tree | Valid about its recorded subject, not evidence about the current tree. |
| Proposed runtime families with no accepted exact identities | Planned population remains distinct from runtime support. |
| Accepted spec with indeterminate forensic associations | Specification authority retained; support associations not promoted or hidden. |

Not every frontend must execute every verifier directly. If the browser is an offline viewer, these are display/import tests. If it has a live backend route, include that route's failure and freshness tests. Record the difference.

## 5. The highest-risk case: the negative test's green status

A successful P9-1.7 negative test has two opposite-looking but compatible facts:

```text
mutated candidate result: REJECTED
harness assertion result: PASSED
```

A CLI summary, API serializer, notebook cell, browser badge, or export must not replace these with an unqualified successful candidate status.

Pressure the complete path:

```text
unauthorized candidate mutation
    -> verifier rejection
    -> passing negative-test assertion
    -> API/notebook/browser projection
    -> exported report
```

At each stage, the candidate remains rejected. Project/runtime permission is unaffected by the harness pass. Inspect the exported file as well as the visible interface; a correctly labelled screen with an overclaiming download is still defective.

Use the converse positive fixture too: a permitted isolated future addition should not be displayed as denied merely because the preserved historical gate contains an older false implementation flag. Different temporal subjects must stay separate.

## 6. Prevent semantic conversion of authority and evidence

### 6.1 No status substitution

Test `false`, missing, null, explicit unknown/unavailable, and unrecognized values according to the actual input schema. An adapter must not turn missing permission into true, and it should not misreport unknown permission as an explicit reviewed denial. Withhold permission in both cases while preserving why.

A transport-success code or successful JSON parse means the response was delivered or decoded. It does not establish historical validity, current-tree admissibility, or runtime authorization. Similarly, a subprocess returning zero without required result fields should not become a complete pass by default.

### 6.2 Keep accepted authority and forensic support separate

P9-REVIEW-001 preserves `indeterminate_requires_review` for the D10.2 contract associations while acknowledging the accepted specification's authority. [S4]

Test that APIs, tables, graph labels, summaries, and exports preserve both statements. Do not strengthen the associations into proved support. Do not weaken the accepted specification into "unusable" because the associations remain indeterminate. Preserve source-local provenance labels as provenance labels, not newly invented queryable claim nodes.

Unknown query identifiers stay unknown. A friendly search suggestion may be displayed separately, but it cannot replace the requested unknown claim with a nearby accepted claim.

### 6.3 Counts retain their denominator and evidence kind

A display of 41 claims, 80 objects, 183 contracts, ten families, or forty compatibility cells describes a particular source population. It is not a count of executed runtime evidence. [S1–S3]

Likewise, the prior 105 core and 763 model regression results are legacy-baseline evidence, not V4 conformance. [S4, S6]

If a renderer offers coverage percentages, require the exact denominator and scope. One historical record, its exported copy, and an evidence alias do not become three independent executions. Reusing evidence for multiple legitimate consumers is allowed, but does not create a new experiment or expand its profile domain.

## 7. Freshness and cross-surface outliers

### 7.1 Notebook freshness

Run from a fresh kernel against the bound input. Then change a relevant source/authority file and rerun the verification path. The previous cell's visible success must not be presented as the new run's result.

Also test out-of-order cell execution and a variable left from another checkout. A saved notebook can retain historical output, but its subject/run must remain identifiable. Kernel execution counts or timestamps alone do not identify the verified inputs.

### 7.2 Browser and API freshness

Where a live route exists, request result A, switch to subject B, and let A finish last. An older response must not overwrite the currently selected subject's status. Test failed refresh, browser reload, and cached API response from a different authority version.

These are applicable asynchronous-consumer tests, not claims that the supplied browser currently has that architecture.

For an offline viewer, the correct output is a report about the loaded artifact. Lack of live checkout access is not necessarily a failure of offline verification, but prevents a claim that the current checkout has just been checked.

### 7.3 Hash and schema fidelity

Use two different full identifiers with the same displayed prefix. They must not collide in selection, caching, copying, or report lookup. Display shortening is acceptable; operational identity remains complete.

Reject or explicitly report unsupported schemas rather than silently assigning success defaults to unknown authority fields. Verify that serialization preserves exact IDs, distinct false/absent values where meaningful, and typed source statuses. Do not use display strings as new authority records.

### 7.4 No hidden read-side writers

Refresh, render, query, export, or rerun a notebook cell must not accept P9-G1, rewrite a frozen release, repair a source claim, append fabricated runtime evidence, or turn a synthetic fixture into a live gate.

Compare protected before/after manifests. Declared report/cache outputs are permitted within their scope; they are not authority writes. If a tool has a separate explicit acceptance action, its authorization remains outside this leaf's read/projection checks.

## 8. Tool documentation and checklist propagation

Update operational instructions to identify the actual normal command and successor route, their input identities, expected scoped conclusions, and known limitations. Keep the distinction between:

```text
historical dedicated release acceptance
current review-tree verification
adversarial test assertion
surface projection check
reviewer acceptance
runtime authorization
runtime conformance
```

A command example with fabricated output must say it is illustrative. A historical example should retain its historical identity and not look like the current run. Test a documented invocation from its declared directory and with missing prerequisites so the failure guidance is truthful.

P9-1.8 should reconcile the tool's own plan/checklist and the Phase-9 leaf records without checking off P9-1.9 or unrelated runtime work. Leaf completion does not imply tranche acceptance; controlled batches retain separate results. [S1–S3]

If a documentation-only rewording would change an authority status, support set, profile scope, or missing-evidence interpretation, treat it as a semantic change requiring review, not typography.

## 9. Artifact and regression expectations

Retain a surface applicability map, bound scenario corpus, raw verifier results, per-surface normalized projections/assertions, commands, actual API responses or notebook outputs, relevant browser evidence, exported files, and protected pre/post manifests.

A screenshot can show a misleading label, but it is not enough to prove which backend produced it or whether a stale report was loaded. Bind screenshots to structured results and input identities. Conversely, schema-valid JSON does not prove that a visible label or export preserves its meaning; inspect both machine and human-facing surfaces.

Regression scope should include existing historical queries and command outputs that the routing change can affect. Do not redesign the entire exploration tool. Keep serialization/transport differences that are genuinely presentation-only, while testing exact semantic agreement on authority, subject, and evidence.

If a required surface cannot execute in the available environment, label it not executed with its dependencies and hold implications. Passing API tests are not browser evidence; browser rendering is not a fresh model runtime execution. The source plan calls for affected-surface consistency, not interchangeable credits. [S1, S2]

## 10. Completion and shared issue reconciliation

P9-1.8 can earn:

> The affected operational and presentation surfaces preserve the same bound verification conclusions, negative-test subjects, authority distinctions, source semantics, freshness limitations, and evidence ceilings.

It cannot grant P9-G1, runtime source permission, profile conformance, scientific support promotion, or a new implementation identity.

Reconcile P9-TOOL-001 at its declared scope using the separately reviewed P9-1.6 route, P9-1.7 adversarial evidence, and P9-1.8 affected-surface evidence. Do not erase its historical failure. If a required surface or adversarial category is pending, keep that condition visible. The opening assigns the issue across these three leaves; P9-1.9 remains the later acceptance action. [S2, S3]

### Suggested handoff statement

```text
P9-1.6: route verified for the bound current review tree
P9-1.7: bounded adversarial matrix reconciled
P9-1.8: affected surface projections reconciled
P9-TOOL-001: closure or remaining conditions stated explicitly
P9-G1: separate review/acceptance still required
runtime support: unchanged by these tool-verification results
```

The next step is a review of those results under the existing P9-1.9 authority process, not an automatic implementation flag change.
